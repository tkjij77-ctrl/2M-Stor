# 2M-Stor — نظام إدارة المخزون والمبيعات

> نظام نقاط بيع ومخزون عربي (RTL) لمتجر آل السيد — يعمل **أوفلاين أولًا** مع مزامنة سحابية فورية عبر Supabase، ويُثبَّت كتطبيق PWA على الموبايل والكاشير.

| البند | القيمة |
|---|---|
| **الحالة** | يعمل في الإنتاج — [tkjij77-ctrl.github.io/2M-Stor](https://tkjij77-ctrl.github.io/2M-Stor/) |

## البنية — مسارَان متوازيان

المشروع يحتوي **نسختين** تعملان جنبًا إلى جنب:

```
┌─ index.html  ← التطبيق الرئيسي المُنشور (4,500+ سطر · ملف واحد)
│    ├─ متجر للعملاء · مخزن · سلة · فواتير · تقارير · إدارة حسابات
│    ├─ المزامنة: outbox في localStorage + Realtime + polling
│    └─ يُنشر مباشرة على GitHub Pages ✅ هذا ما يستخدمه المحل فعليًا
│
└─ app/  ← نسخة Next.js 15 (تجريبية — لم تكتمل)
     ├─ app/(shop) · components/ · lib/sync/ · lib/db/
     ├─ lib/db/indexedDB.ts — تخزين IndexedDB بدل localStorage
     ├─ lib/sync/realtime.ts — postgres_changes
     └─ ⚠️ تحتاج إصلاح CSS + سلة حقيقية (انظر docs/)
```

> **ملاحظة مهمة:** `index.html` هو المصدر الحقيقي للتصميم والمنطق. نسخة Next.js مشروع ترقية قيد العمل — لا تفترض أنها متطابقة.

## الملفات الأساسية

| الملف | الوصف |
|---|---|
| `index.html` | **التطبيق كامل** (واجهة + منطق + مزامنة) — ملف مونوليث واحد |
| `sw.js` | Service Worker: NetworkFirst للتنقل + كاش للأوفلاين + تحديث تلقائي |
| `manifest.json` | تعريف الـ PWA (الاسم، الأيقونات، الوضع المستقل) |
| `cloud-schema.sql` | مخطط قاعدة البيانات الكامل (جداول + سياسات RLS + Storage) |
| `supabase/migrations/` | ملفات الترحيل — **مصدر الحقيقة لبنية قاعدة البيانات** |
| `docs/rls.md` · `docs/sync.md` | توثيق سياسات الأمان ومنطق المزامنة |
| `plane.md` | خطة التطوير والمراحل السابقة |
| `security-fixes.sql` | إصلاحات أمنية جاهزة (تشخيص + تنفيذ + تحقق) |
| `tests/` | اختبارات Vitest (وحدات) + Playwright (E2E) |

## التشغيل محليًا

### التطبيق الرئيسي (`index.html`) — لا يحتاج بناء

```bash
# أي واحدة من الطريقتين:
python3 -m http.server 8080        # ثم افتح http://localhost:8080
npx serve .                        # أو
```

> ⚠️ لا تفتحه بـ `file://` مباشرة — Service Worker والـ fetch يحتاجان خادمًا.

### نسخة Next.js

```bash
npm ci
cp .env.example .env.local         # ضع مفاتيح Supabase الخاصة بك
npm run dev                        # http://localhost:3000
```

## إعداد السحابة (لمرة واحدة)

راجع الدليل المفصل: **`cloud-setup-guide.md`**

الملخص:
1. أنشئ مشروعًا على [supabase.com](https://supabase.com)
2. نفّذ `cloud-schema.sql` ثم ملفات `supabase/migrations/*.sql` في SQL Editor
3. أنشئ bucket باسم `products` (عام للقراءة)
4. Authentication → فعّل **Confirm email** + **Leaked password protection**
5. في التطبيق: ⚙️ الإعدادات ← ☁️ الاتصال السحابي ← ضع `Project URL` + `anon key`

> 🔑 **`anon key` عام بالتصميم** (موجود في كود الموقع) — الأمان الحقيقي في سياسات RLS.
> 🔒 **`service_role key` سري** — لا تضعه في أي ملف بالمستودع ولا في كود المتصفح.

## الأمان — قواعد ملزمة

| القاعدة | السبب |
|---|---|
| لا تكتب أي كلمة مرور في الكود | كان `admin/admin` وحساب الزائر المشترك مكتوبَين — أُزيلا في التحديث الأمني |
| أي حساب جديد = `customer` دائمًا | الترقية إلى `worker`/`admin` من «إدارة الحسابات» فقط، والحماية في تريغر قاعدة البيانات |
| عميل لا يقرأ فواتير غيره | سياسة `inv_read` تسمح له بطلباته فقط |
| لا تستدعِ دوال SQL حساسة من العميل | `my_role()` و`my_username()` مُقيّدة بـ `authenticated` |
| خُد نسخة احتياطية قبل أي تعديل SQL | لا يوجد Versioning على الخطط المجانية |

**قبل تعديل أي سياسة RLS:** نفّذ قسم الفحص التشخيصي في `security-fixes.sql` أولًا، وجرّب على مشروع Supabase تجريبي قبل الإنتاج.

## سير العمل (مهم للمساهمين)

```
main  ──── محمي: لا دفع مباشر ──── يجب PR + نجاح الفحوصات
  └─ فرع → تعديل → PR → مراجعة → دمج
```

- كل تعديل على `index.html` = فرع منفصل + معاينة قبل الدمج
- بعد أي تغيير في الواجهة: **ارفع رقم `CACHE` في `sw.js`** ليصل التحديث للأجهزة
- لا تخلط تعديلات قاعدة البيانات مع تعديلات الواجهة في PR واحد
