# 2M-Stor — نظام إدارة المخزون والمبيعات

> نظام نقاط بيع ومخزون عربي (RTL) لمتجر آل السيد — يعمل **أوفلاين أولًا** مع مزامنة سحابية فورية عبر Supabase، ويُثبَّت كتطبيق PWA على الموبايل والكاشير.

---

## نظرة سريعة

| البند | القيمة |
|---|---|
| **الحالة** | يعمل في الإنتاج — [tkjij77-ctrl.github.io/2M-Stor](https://tkjij77-ctrl.github.io/2M-Stor/) |
| **الإصدار** | v3.3 (التطبيق) · sw v30 (كاش) |
| **الواجهة** | عربي RTL · فاتح/داكن · متجاوب من 320px إلى 1400px+ |
| **قاعدة البيانات** | Supabase (PostgreSQL 15+) مع Row Level Security |
| **الاستضافة** | GitHub Pages (التطبيق الرئيسي) · Vercel (نسخة Next.js تجريبية) |

## البنية — مسارَان متوازيان

المشروع يحتوي **نسختين** تعملان جنبًا إلى جنب:

```
┌─ index.html  ← التطبيق الرئيسي المُنشور (4,500+ سطر · ملف واحد)
│    ├─ متجر للعملاء · مخزن · سلة · فواتير · تقارير · إدارة حسابات
│    ├─ المزامنة: outbox في localStorage + Realtime + polling
│    └─ يُنشر مباشرة على GitHub Pages ✅ هذا ما يستخدمه المحل فعليًا
│
└─ app/  ← نسخة Next.js 15 (تجريبية — لم تكتمل)
     ├─ app/(shop) · components/ · lib/sync/ · lib/db/
     ├─ lib/db/indexedDB.ts — تخزين IndexedDB بدل localStorage
     ├─ lib/sync/realtime.ts — postgres_changes
     └─ ⚠️ تحتاج إصلاح CSS + سلة حقيقية (انظر docs/)
```

> **ملاحظة مهمة:** `index.html` هو المصدر الحقيقي للتصميم والمنطق. نسخة Next.js مشروع ترقية قيد العمل — لا تفترض أنها متطابقة.

## إعداد السحابة (لمرة واحدة)

راجع الدليل المفصل: **`cloud-setup-guide.md`**

الملخص:
1. أنشئ مشروعًا على [supabase.com](https://supabase.com)
2. نفّذ `cloud-schema.sql` ثم ملفات `supabase/migrations/*.sql` **بالترتيب** في SQL Editor
   (آخرها `20260921070000_login_throttle.sql` — قفل محاولات الدخول على السيرفر)
3. أنشئ bucket باسم `products` (عام للقراءة)
4. Authentication → فعّل **Confirm email** + **Leaked password protection**
5. في التطبيق: ⚙️ الإعدادات ← ☁️ الاتصال السحابي ← ضع `Project URL` + `anon key`

> 🔑 **`anon key` عام بالتصميم** (موجود في كود الموقع) — الأمان الحقيقي في سياسات RLS.
> 🔒 **`service_role key` سري** — لا تضعه في أي ملف بالمستودع ولا في كود المتصفح.

### 6. الترتيب الصحيح للترحيلات (مهم)

```
supabase/migrations/
  20260826200407_baseline.sql              ← الأساس (جداول + سياسات)
  20260827104851_add_invoice_status.sql    ← حالة الفاتورة
  20260921000000_security_hardening.sql    ← إصلاحات الأمان
  20260921010000_soft_delete_rls.sql       ← الحذف الناعم + سلة المحذوفات
  20260921020000_stock_model.sql           ← تتبّع المخزون + قيود السلامة
  20260921030000_stock_rpc.sql             ← دالتا خصم/إرجاع المخزون (ذرّيتان)
  20260921040000_invoice_numbering.sql     ← ترقيم الفواتير المركزي
  20260921050000_rls_anon_access.sql       ← إصلاح عطل الزائر (N-1/N-2)
  20260921060000_role_guard_service_role.sql ← تهيئة أول مدير (N-3)
  20260921070000_login_throttle.sql        ← قفل محاولات الدخول (F2)
```

نفّذها **بالترتيب** في SQL Editor. كلها آمنة للتشغيل المتكرر (idempotent).
بعدها: `scripts/grant-role.sql` لترقية حسابك إلى مدير (تعديل سطر واحد)، ثم
`scripts/health-check.sql` لفحص 13 بندًا في شاشة واحدة.

### 7. اختبار سياسات الأمان فعليًا (موصى به بشدة)

بدل افتراض أن السياسات سليمة، **اختبرها**:

```

```

يُنشئ حسابات اختبار مؤقتة (تُحذف تلقائيًا)، ويفحص 4 أدوار × 8 جداول:
هل يستطيع الزائر الكتابة؟ هل يستطيع العميل ترقية نفسه إلى مدير؟
يُنفَّذ داخل معاملة واحدة ويُنفّذ `rollback` — **لا يترك أثرًا**.

### 10. المخزون — البيع يخصم فعلًا

| الإعداد | المعنى |
|---------|--------|
| **المخزن والمعروض معًا** (افتراضي) | البيع ينقص الرصيدين — الجرد يطابق الواقع |
| **المعروض فقط** | الوضع القديم: الرصيد الإجمالي لا يتأثر بالبيع |
| **لا تخصم تلقائيًا** | للمحلات التي تفضّل الجرد اليدوي |

- إلغاء الطلب أو رفضه أو حذف الفاتورة ← **تُرجَع الكميات** تلقائيًا
- البيع برصيد غير كافٍ: تنبيه (افتراضي) أو منع نهائي — حسب الإعداد
- الكميات لا تنزل تحت الصفر أبدًا

```sql
-- تقرير الجرد (بعد تنفيذ 20260921020000_stock_model.sql)
select * from public.stock_health;              -- أين التناقض والأصناف الناقصة
select * from public.stock_mismatch_report();   -- فواتير ملغاة لم تُرجِع كمياتها
select public.revert_invoice_stock(1234);       -- إرجاع كميات فاتورة يدويًا
```

> ⚠️ **عند تحويل الوضع إلى «المخزن والمعروض معًا»**: راجع أرقام المخزن مرة واحدة،
> لأن الفواتير القديمة خصمت «المعروض» فقط. الفواتير القديمة عند إلغائها تُرجع
> المعروض فقط — وهو الصحيح (لم يُخصم مخزنها أصلًا).

### 11. المزامنة — ماذا يحدث لو انقطع الإنترنت؟

- كل تغيير يدخل **طابورًا** يُرفع للسحابة تلقائيًا
- ⚙️ الإعدادات ← 🔄 **حالة المزامنة**: ما ينتظر الرفع، وما فشل وسببه
- عملية فاشلة **لا تعطّل** بقية الطابور — تُعزل مع سبب واضح
- فشل عابر (شبكة/سيرفر) يُعاد تلقائيًا بتأخير متزايد — بلا تدخّل منك
- الشريط العلوي يبيّن: `⏳ 3 بانتظار الرفع` أو `⚠️ عملية فشلت`
- التعديلات المكرّرة على نفس الصنف تُدمج (لا 20 طلبًا لـ20 تعديلًا)

### 12. الحذف الناعم — لا شيء يضيع

حذف أي صنف أو قسم **لم يعد نهائيًا**:

- الحذف يضع `deleted_at` بدل مسح الصف
- ⚙️ الإعدادات ← 🗑️ **سلة المحذوفات** → استعادة بضغطة
- حذف قسم **لا يمحو أصنافه** (كان يمحوها بالتسلسل قبل الإصلاح)
- تنظيف تلقائي لما تجاوز 90 يومًا (`purge_old_trash()`)
- زر «ارفع المتجر للسحابة» **يؤرشف** القديم ولا يمسحه (ولا يمسّ الفواتير)

### 13. سلة المتجر — مشتركة ومحفوظة

المتجر (`/`) عنده سلة حقيقية واحدة تعمل على كل الصفحات:

- **لا تضيع**: الإضافة تُحفظ فورًا (تغلق المتصفح وترجع — نفس السلة)
- شارة العدد في الرأس تتحدّث مع كل إضافة أو حذف
- صفحة `/cart`: تعديل الكميات · حذف سطر · كود خصم · شحن وضريبة من الإعدادات
- **لا يمكن تجاوز المتاح**: الكمية تُحصر في رصيد الصنف، ووضع `منع` يمنع الإتمام
- رقم الشحن/الكوبون/الضريبة تُقرأ من جدول `settings` السحابي — لا أرقام في الكود
- الإتمام **يتطلب تسجيل دخول** (نفس حساب التطبيق) ويدخل الطابور إن انقطعت الشبكة

> 🔐 **المخزون يُخصم على السيرفر** بدالة `decrement_stock` الذرّية — لا يرسل
> العميل رقمًا نهائيًا يمكن التلاعب به، وكل تغيير يُسجَّل في سجل التدقيق.

### 13-صفر. المخطط: المستودع هو المرجع (T3.7)

- **فحص الانحراف**: `node scripts/verify-schema-drift.js` — فحص ذاتي بلا إنترنت
  (جداول · RLS · سياسات · RPC يستدعيها التطبيق · دلو الصور · Realtime · الوثائق).
- **مقارنة بالقاعدة الحقيقية**: نفّذ `scripts/schema-inventory.sql` في SQL Editor،
  انسخ الناتج إلى ملف، ثم `node scripts/verify-schema-drift.js inventory.txt`.
  أي سطر «على القاعدة وليس في المستودع» يعني أن إعادة البناء من المستودع ناقصة.
- **مسوّدة ترحيل**: أضف `--emit-migration supabase/migrations/x.sql` مع نسخة `pg_dump`
  ليكتب تعريفات ما على القاعدة فقط، لتراجعها وتلتزمها. المسوّدة **آمنة الإعادة**
  (`drop policy if exists … on جدول` + `create … if not exists`) فتُنفَّذ على نفس القاعدة بلا خطأ.
- **الوثائق مربوطة بالفحص**: `docs/rls.md` و`docs/sync.md` يفشل الفاحص إن لم تطابق الواقع
  (الأرقام تُفحص **صفًّا صفًّا** لا بمجرد وجود الرقم في الملف).
- **دورة كاملة مُختبَرة**: `bash scripts/verify-drift-modes.sh` — تبني قاعدة، تجردها،
  تقارنها، تصدر مسوّدة وتنفّذها. كشفت هذه الدورة خمسة عيوب حقيقية في الأداة أُصلحت
  (تسبيق `public.` · أعمدة `add column` متعددة في عبارة · دوال الإضافات · جداول `storage`
  ومشغّلات `auth` · مسوّدة لا تُنفَّذ).

### 13-صفر-ب. قفل محاولات الدخول (F2)

القفل **على السيرفر** لا في المتصفح: جدول `login_attempts` (revoke كامل + بلا سياسات عن
قصد — الوصول بالدوال فقط) ودوال `login_gate` · `login_fail` · `login_ok`.

| المستوى | الحد | العقوبة |
|---|---|---|
| اسم المستخدم | 5 / 15 دقيقة | 5 دقائق تتضاعف ×2 حتى ساعة |
| الجهاز | 15 / 15 دقيقة | 15 دقيقة |
| الشبكة (IP) | 40 / 15 دقيقة | 30 دقيقة |

الواجهة تفحص **قبل** إرسال المحاولة، وتُظهر ما بقي، وتعمل بلا إنترنت بقفل محلي متصاعد
تُفصح أنه محلي. الإثبات: `node scripts/verify-login-throttle.js` (18 فحصًا في متصفح
حقيقي — منها أن مسح بيانات المتصفح لا يُلغي القفل).

### 13-أ. الهوية والصفحات القانونية

- **وصف المتجر** يُحرَّر من الإعدادات (`store_desc`) — لا نص ثابت في الكود
- **بيانات التواصل** تُعرض من الإعدادات فقط؛ وإن غابت يقول الموقع ذلك صراحة
- **٣ صفحات قانونية**: `/privacy` · `/terms` · `/returns` (ونتائجها في التطبيق الرئيسي عبر تذييل الصفحة)
- **سياسة الإرجاع يحدّدها المالك**: مدة الإرجاع (0 = «لم تُحدَّد بعد») + شروط إضافية
- **لا وعود بلا أساس**: أُزيل «إرجاع 14 يوم» و«دفع آمن» و«توصيل 24 ساعة» وتقييم
  «4.3» المبني على المخزون — والنظام يقول بصراحة إنه لا يجمع تقييمات

### 13-ب. أرقام الفواتير — تسلسل واحد لكل الأجهزة

- الرقم الرسمي يأتي من دالة `next_invoice_no()` على السيرفر (تسلسل مركزي)
- **بلا اتصال**: الفاتورة تأخذ رقمًا مؤقتًا معلَّمًا (`noTemp`) — البيع لا يتوقف
- عند الرفع: إن كان الرقم محجوزًا على جهاز آخر يُسند السيرفر رقمًا بديلًا
  والتعليم الجديد يُثبَّت في السجل المحلي تلقائيًا
- الفجوات في التسلسل **مقصودة** (رقم أُسند ولم تُحفظ فاتورته) — الفجوة أرحم من التكرار

### 14. حوكمة التبعيات (لا ثغرات صامتة)

- **`npm audit` = صفر ثغرات** (كانت 12، منها 1 حرجة): ترقية `vitest` + `overrides`
  مثبّتة في `package.json` لـ`serialize-javascript` و`postcss`
- **Dependabot** يفتح طلبات تحديث أسبوعيًا (npm + إجراءات GitHub)، والترقيات الكبرى
  في طلب منفصل لا يُدمج تلقائيًا
- **CodeQL** يفحص كل دفع وطلب دمج وكل أسبوع — النتائج في تبويب Security
- **بوابة في CI**: ثغرة عالية أو حرجة تُفشل البناء
- فحص الإعدادات محليًا: `python3 scripts/verify-ci-config.py` (19 فحصًا)

> ⚠️ استخدم `npm ci` لا `npm install --force` — الـoverrides هي ما يبقي العدد صفرًا.
> ⚠️ **قيد معروف**: CodeQL لا يفحص الشيفرة المضمّنة داخل `index.html` — لذلك
> تفكيك الملف (T5.1) شرط لشمول الفحص الأمني الكامل.

## الأمان — قواعد ملزمة

| القاعدة | السبب |
|---|---|
| لا تكتب أي كلمة مرور في الكود | كان `admin/admin` وحساب الزائر المشترك مكتوبَين — أُزيلا في التحديث الأمني |
| أي حساب جديد = `customer` دائمًا | الترقية إلى `worker`/`admin` من «إدارة الحسابات» فقط، والحماية في تريغر قاعدة البيانات |
| عميل لا يقرأ فواتير غيره | سياسة `inv_read` تسمح له بطلباته فقط |
| لا تستدعِ دوال SQL حساسة من العميل | `my_role()` و`my_username()` مُقيّدة بـ `authenticated` |
| خُد نسخة احتياطية قبل أي تعديل SQL | لا يوجد Versioning على الخطط المجانية |

**قبل تعديل أي سياسة RLS:** نفّذ قسم الفحص التشخيصي في `security-fixes.sql` أولًا، وجرّب على مشروع Supabase تجريبي قبل الإنتاج.

## سير العمل (مهم للمساهمين)

```
main  ──── محمي: لا دفع مباشر ──── يجب PR + نجاح الفحوصات
  └─ فرع → تعديل → PR → مراجعة → دمج
```

- كل تعديل على `index.html` = فرع منفصل + معاينة قبل الدمج
- بعد أي تغيير في الواجهة: **ارفع رقم `CACHE` في `sw.js`** ليصل التحديث للأجهزة
- لا تخلط تعديلات قاعدة البيانات مع تعديلات الواجهة في PR واحد
