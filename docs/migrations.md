# سياسة الترحيل على قاعدة الإنتاج (T1.5)

القاعدة المجانية في Supabase **بلا PITR**، والتطبيق يستخدمه محلّ حقيقي يعمل يوميًا.
لذلك: «لا تجرّب على الإنتاج» لا تعني ألّا ترحّل أبدًا — بل أن يكون كل ترحيل محاطًا بضمانات.

## الطريقة الملزمة

```bash
# 1) معاينة بلا تعديل
bash scripts/safe-migrate.sh supabase/migrations/20260922120000_client_errors.sql --dry-run

# 2) التنفيذ (نسخة احتياطية → معاملة واحدة → تحقق → إرجاع عند الفشل)
bash scripts/safe-migrate.sh supabase/migrations/20260922120000_client_errors.sql

# حالة القاعدة كما هي الآن
bash scripts/safe-migrate.sh --status
```

كلمة مرور القاعدة في `~/.priv/db_password` (صلاحيات 600) أو المتغيّر `SUPABASE_DB_PASSWORD`
— **ولا تُكتب أبدًا داخل المستودع**. بديل بلا كلمة مرور: لصق `scripts/apply-backend-all.sql`
في Supabase → SQL Editor.

## ما يفعله السكربت بالترتيب

| الخطوة | الضمان |
|---|---|
| فحص الاتصال | نتوقف فورًا لو كلمة المرور/الشبكة خطأ — لا تعديل جزئي |
| لقطة «قبل» | عدّادات الأصناف والفواتير والحسابات و`stock_q` تُقاس قبل التنفيذ |
| نسخة احتياطية كاملة | `pg_dump` إلى `~/.priv/backups/pre-migrate-<وقت>.sql` (600) |
| التنفيذ | `psql --single-transaction -v ON_ERROR_STOP=1` ⇒ **إما الملف كله أو لا شيء** |
| لقطة «بعد» | مقارنة باللقطة السابقة؛ أي تغيّر في بيانات تشغيلية أثناء ترحيل بنيوي يُطبع تحذيرًا |
| تحقق من الكائنات | كل جدول/دالة وعد بها الملف تُفحص فعليًا (وجود · عدد صفوف · RLS مفعّل) |

## قواعد لا تُخالَف

1. **كل ترحيل بلا استثناء** يمرّ من `safe-migrate.sh` — لا `psql` يدوي على الإنتاج.
2. **لا حذف بيانات** في ترحيل: الحذف عملية تشغيلية لها `soft delete` وسلة محذوفات.
3. **كل ملف ترحيل idempotent** (`if not exists` / `create or replace` / `drop policy if exists`)
   فيمكن إعادة تنفيذه بلا كسر.
4. **كل تغيير في المخطط يُحدَّث معه** `docs/rls.md` (الأعداد مربوطة بفحص آلي:
   `node scripts/verify-schema-drift.js --repo`) و`scripts/apply-backend-all.sql`
   (`bash scripts/build-apply-backend-all.sh`).
5. **نسخة احتياطية يومية مستقلة** تعمل عبر `.github/workflows/backup.yml` (تحتاج أسرار
   `SUPABASE_ACCESS_TOKEN` · `SUPABASE_DB_PASSWORD` · `SUPABASE_PROJECT_REF`).

## المثالية التي لم نصل إليها بعد

الطريقة الصحيحة تمامًا هي **مشروع Supabase تجريبي** يُجرَّب عليه كل ترحيل قبل الإنتاج.
كلمة مرور قاعدة الإنتاج لا تكفي لذلك (تحتاج مشروعًا ثانيًا). حتى يُنشأ، تُغطّي الضمانات أعلاه
(نسخة + معاملة ذرّية + تحقق) معظم المخاطر، ويبقى الفارق: لو كان الترحيل **منطقيًا** خاطئًا
فإنه سينجح تقنيًا على الإنتاج. لذلك أي ترحيل يمسّ بيانات قائمة (لا بنية فقط) يحتاج مراجعة
يدوية قبل التنفيذ.
